# 小熊猫音乐实机反馈：音源限制与下一步对照（2026-11-04）

用户已烧录带 `Opus quality:` 的音乐音质修订，仍觉得原曲播放不够优质，并确认使用小智官方
平台，没有自建音乐服务。这是对上一轮软件候选的真实负面听感反馈，不能继续描述为“音质已验收”。

## 本次日志确认的事实

| 指标 | 记录 |
| --- | --- |
| 可统计音乐时长 | 12 个三秒窗口，共 36 秒 |
| 音乐包数 | 600 |
| 实际负载平均码率 | 27,382 bps；范围 27,248～27,554 bps |
| 编码声道/模式 | 全部 mono、全部 CELT；不是误用 SILK 语音模式 |
| 编码带宽 | 全部为 12 kHz（SWB） |
| 解码/输出采样率 | 均为 24 kHz |
| 解码前端输出峰值 | 25,169 / 32,768 |
| PCM 满幅边界命中/解码失败 | 均为 0 |
| 提供片段内 AFE 队列溢出/看门狗告警 | 未记录 |
| 神经上行超预算 | 两次：33,725/32,000 us 和 32,033/32,000 us |

这些数据证明收到的音乐是约 27.4 kbps 的单声道 Opus，但**不能证明低码率是所有听感问题的
唯一原因**。编码带宽是格式能力，不等于原曲真实频谱；PCM 不满幅不等于功放、喇叭不失真；
未记录队列溢出也不等于已测得网络零丢包。两次上行偶发超时不能直接归因为音乐解码破音。

[Opus RFC 6716 §2.1.1](https://www.rfc-editor.org/rfc/rfc6716.html#section-2.1.1)
给出的 fullband 单声道音乐参考甜点区为 48～64 kbps（以 20 ms 帧为条件）。本机 SWB/24 kHz
链路与该条件不完全相同，该范围可以指导高质量对照，不能当作一条低于就必差的硬门槛。
[RFC §2.1.2](https://www.rfc-editor.org/rfc/rfc6716.html#section-2.1.2) 也明确支持单声道音乐；
本板只有单扬声器，所以不以“改成立体声”作为必要的音质改进。

## 为什么本轮没有再改 EQ 或发一个新固件

本工程两种传输的 `GetHelloMessage()` 仅发送现有格式/采样率/声道/帧长，没有得到确认的
“指定官方音乐下行码率”契约。调高本机麦克风 Opus 编码码率只影响上行；把 27 kbps 到达的
音乐转成 64 kbps 文件，或只改为 48 kHz 播放，也不能恢复源流已丢弃的信息。

本轮没有修改官方平台配置、现有扬声器参数、音量、采样时钟或人声打断实现，没有宣称已
完成对官方音源的高码率改造。保留 `81d4fce` 固件，避免在没有硬件频响/原曲对照时继续
叠加未知均衡。此次只增加分析文档和可复核试听材料，无固件代码改动，未重复构建/烧录。

## 已准备的同源对照

`dist/wzh-tailredpanda-music-source-check-20261104/` 提供：

- `music-28k.opus`：24 kHz 单声道输入，20 ms 帧，CBR 28 kbps。
- `music-64k.opus`：其他编码条件相同，仅目标码率为 64 kbps。
- 两个 `*-same-dsp.wav`：分别解码到 24 kHz 后，经当前生产 `SpeakerProtection`，
  保持相同输入电平、EQ、RMS/峰值保护和音量设定；没有事后响度归一化。
- `music-reference-same-dsp.wav`：同一未压缩输入经相同 DSP，作第三个参照。
- `comparison.json`：实际测得包负载码率、峰值、电平和源文件 SHA-256；`log-summary.json`
  是本次用户日志的聚合指标，不包含原始对话内容。

素材是上一轮自合成的 12 秒器乐/打击乐，不是用户所播原曲，也不包含人声。实际输出码率约
28.04 与 64.09 kbps，DSP 后 RMS 相差约 0.010 dB，峰值均为 27,524；这不是主观试听评分。
自审逐包核对：两个文件均为 CELT/mono；28 kbps 编码器在起始少量包自动选择 8 kHz，
其余为 12 kHz，64 kbps 为 12 kHz。因此这是不同码率配置的说明性对照，不是严格全段
同带宽的实验；具体包数在 JSON 中，不能据此声称官方原曲的听感差异已得到测量。
官方原流的具体编码器、参数和多次转码历史未知，该材料只是单变量对照，不能称为原服务复现。

电脑/手机播放 WAV 只能帮助比较编码损失，不能验证小熊猫的喇叭。现有本地 Opus 解码链可以
支持这些编码包，但本轮没有往外置 Flash 写入样本，也没有在本机实际播放这套材料。

## 建议的处理顺序与可选架构

1. 先在同一只小熊猫、同一音量及相近电池状态，用**同一段真实原曲**作高质量本地文件与
   官方播放的对照。若只有官方流明显粗糙，优先更换/提高音乐音源与转码质量；若两者都闷
   或破，再测功放输出、喇叭频响、腔体/机身共振。当前没有该原曲文件和机上录音，不能
   给出硬件与编码分别占比，也不据此建议购买或更换器件。
2. 要保留官方对话而绕开当前官方音乐编码，可考虑**设备侧音乐 MCP 工具＋高质量音频直链**。
   这需要真实可用的音乐源，不是往原 `play_music` 调用里随意加 `bitrate=64000`。
3. 已核实的工程参考有
   [Maggotxy 音乐固件](https://github.com/Maggotxy/xiaozhi-esp32-music/blob/main/README.md)
   和 [xiaozhimusic](https://github.com/wuooo339/xiaozhimusic/blob/master/README.md)。它们提供设备侧
   工具/网络音乐路线，未在本板验证，不能因 README 写高质量就承诺实机效果。
   [上游维护者在 #863 的说明](https://github.com/78/xiaozhi-esp32/issues/863) 还要求其 MP3
   播放方案先退出语音对话；因此不能直接替换掉本项目正在测试的双工人声打断。
4. 如果实施直链方案，需要复用唯一 `AudioService`/ES8311 路径、有界下载与解码缓冲、明确的
   播放所有权/退出/重连语义，并重新验收普通人声打断。当前不能把其他固件的 I2S 播放器
   直接拷进来并声称与本项目兼容。本轮没有接入未经验证的公共音乐 API 或导入第三方固件。
