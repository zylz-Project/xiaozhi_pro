# 三款设备的语音内存与延迟治理

适用范围：爬行熊猫、摇尾小熊猫、恐龙的 ESP32-S3 固件。三个板型共用
`boards/common/wzh/voice_tts`，但硬件、唤醒模型和板级配置各自独立。不要将某一
板型的引脚、内存配置或实测结果视为其他板型的验证。

## 已确认的问题与边界

爬行熊猫一次实机日志中，阿里 HTTP 请求到第一段 PCM 需要约 1.8–2.7 秒；
长回复可能对多段文本分别建立请求。测量不包括用户说话结束到文本到达设备的
全部时间，也不能代表其他网络或云服务负载。播放预缓冲可以吸收抖动，但会
增加首声等待，无法消除服务端合成和逐段建连的延迟。

另一次当前已烧录版本的监视中，首个请求到首段 PCM 为 2.534 秒，首段 PCM
到第一帧进入播放队列为 0.960 秒；同一轮后续请求首包约 2.263 秒。播放队列
的时间并非声学输出时间，以上仅为该次样本，且未刷入本文所述新内存改动。

诊断期间曾观察到内部内存低水位约 7 KB；空闲 PSRAM 较多不代表 DMA、Wi-Fi、
蓝牙或 TLS 所需的内部连续内存充足。当前爬行熊猫的外部 BSS 和小块分配策略
需要同时验证 Flash 操作期间的安全性、内存碎片和 Wi-Fi/蓝牙稳定性；它们尚未
经另外两个板型的硬件验证。不能保证有限内存设备在所有输入、并发和网络条件下
绝不分配失败，目标应是明确容量、避免无界分配、保留关键资源并安全降级。

## 推荐演进

1. 保持设备侧音频、交互状态、云服务提供商三个边界。现有 HTTP/SSE 路径保留为
   可用的兼容路径；声音身份、语言与模型不因传输切换而改变。
2. 为阿里提供有界的 WebSocket 双向流式会话：一轮回复只建立一个合成任务，
   文本陆续发送，二进制 PCM 持续进入既有有界播放队列；结束时发送 finish，
   收到任务结束后才回收。官方文档列出的模型与当前注册音色的目标模型一致。
   是否复用跨轮连接应由实机测量内部内存、重连与认证后决定。
3. 网络、音频和主事件循环之间必须支持背压、超时和取消，禁止在主事件循环
   和音频任务上等待网络。限制文本、WebSocket 消息、PCM 总量及队列长度；
   校验任务 ID、事件顺序、音频格式和 TLS 证书，不记录密钥与用户内容。
4. 仅在确认文本尚未提交云端时允许本轮自动回退到 HTTP；已提交或已播放后
   不盲目重发，以免重复收费或重复播放。取消与新对话用代际标识隔离，旧任务
   的结果不得进入新会话。
5. 将资源预算按内部可分配内存、最大连续块、DMA、PSRAM 和任务栈分别测量。
   在所有板型、全部主要功能与故障注入中确定门限；门限不足时提供明确提示或
   恢复路径，不能把某一次实验值当作所有设备的通用保证。

### Flash 操作与外部栈

音色选择与复刻任务不只是网络处理，还会读写 NVS；不能简单把整个任务栈移到
PSRAM，因为写 Flash 时缓存可能关闭。乐鑫开源的
[`esp_flash_dispatcher` 1.0.3](https://components.espressif.com/components/espressif/esp_flash_dispatcher/versions/1.0.3/readme?language=en)
将列出的 SPI Flash 操作转发到内部栈任务。其声明支持 IDF >= 5.2；隔离工程已在
本机 IDF 6.0.2 编译，并通过 ELF 反汇编确认 `esp_partition` 读写调用被包装。
这还不是硬件验证，也不证明项目外接 W25N/W25Q 的 SPI DMA 或所有缓存关闭路径
安全。调度器本身也需要常驻内部栈和同步对象，内存预算必须把它们计入。

现在以默认关闭的 `CONFIG_WZH_VOICE_FLASH_DISPATCH_EXPERIMENT` 条件接入，音色
录制和选择任务只有在调度器初始化成功后才使用外部栈；初始化失败保留内部栈
尝试。合成工作栈也使用同样的条件。实验路径使用常驻工作任务，避免外部栈任务
自删除时额外创建内部栈清理任务。初始化失败时的全系统行为仍须实测，不能把
单一任务的回退等同于整机回退。

还须逐项检查 NVS、加密分区、OTA、文件系统、外接 Flash 的 DMA 指针、并发取消
及任务生命周期；使用 IDF 堆追踪和任务栈高水位覆盖三款硬件，再决定是否设为
默认。不能把所有任务一键迁入 PSRAM。

当前默认固件仍使用 HTTP/SSE。实验性的 WebSocket 任务和协议校验已接入共享
语音层，但 `CONFIG_WZH_ALI_STREAM_EXPERIMENT` 默认关闭，尚未完成实机及所有
故障路径验证，不应视为已发布方案。现有 HTTP 内存优化包括复用 PCM 解码缓冲，
减少 SSE 音频事件的临时副本；该优化不保证降低云端的合成延迟。

2026-11-13 爬行熊猫实验：实际建立流式任务并播放复刻音色。多轮从进入回复
到首段 PCM 约 1.6–3.1 秒；约 40 秒的长回复记录 4 次缓冲等待，合计约 2.7 秒。
一轮等待更长且触发语音打断检测，不能据此断定打断一定来自用户人声或设备
自身回声。该次实验的内部 SRAM 最低水位约 7 KB；语音切换音色的任务未启动，
原因尚未区分。实验结束后已恢复测试前备份的应用。以上均不能代表其他板型。

随后原应用上复测“切换音色”：任务启动后，语音提示检查到内部可用约 29 KB、
最大连续块 6144 字节，未达到 8192 字节门限，流程失败。尝试只把合成工作栈
移至 PSRAM 后，另一轮在启动选择任务时可用约 40 KB、最大连续块 8192 字节，
但选择任务自身需要 10240 字节，仍未能启动。该 PSRAM 工作栈实验版目前仍在
测试设备上；它不是完整修复，默认构建未启用该实验。

## 发布验证

每个生产板型分别记录：启动、Wi-Fi、BLE、小程序、对话、复刻、声音播放、
配网、管理页与适用的动作/显示/摄像头功能；确认普通语音、已有复刻音色、
预览和音色管理完整。覆盖短/长回复、弱网、断网恢复、取消及打断、连续多轮、
同时连接蓝牙、音频播放、唤醒、适用的 AEC，及 Flash/NVS 操作。分别记录
说话结束到识别、文本到达、首个云端音频、设备首声、句间断流和整轮结束时间，
记录最大连续块与低水位，长期循环后检查泄漏和功能恢复。需要量产前由产品团队
依据真实网络与交互场景设定阈值，并保留安全回退固件；编译和模拟测试不能
代替三款硬件实测。
